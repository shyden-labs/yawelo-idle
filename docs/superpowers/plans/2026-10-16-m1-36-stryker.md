# #36 Stryker mutation testing on the economy and memory code: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task by task. Steps use checkbox (`- [ ]`) syntax for tracking. Tasks 1 to 3 were executed as commits before this plan was written, and their code blocks are those commits' diffs.

**Goal:** CI runs Stryker over the nine economy and memory modules of `packages/core/src` on every pull request that touches what that run reads, fails under a mutation score of 90 and on any drop in it (any undetected mutant not on the committed list of equivalents), uploads the HTML report, and is a required check on `develop`.

**Architecture:** `stryker.config.json` mutates the nine modules and kills each mutant with `packages/core`'s unit tests, driven through `vitest.stryker.config.ts` (a non-unit suite with no limit of its own), and drops mutants that do not compile. A new workflow, `mutation.yml`, has one job, `mutation`, on every pull request. `scripts/ci-scope.ts`, the docs-only classifier (#360), also writes a `mutation=run|skip` verdict from the same diff, so the job always reports and runs Stryker only when needed.

**Tech Stack:** `@stryker-mutator/core`, `@stryker-mutator/vitest-runner` and `@stryker-mutator/typescript-checker` 10.0.0 (Apache-2.0); Vitest 5.0.3; GitHub Actions; the repo's floors (recorded in CI by the `record-floors` label, #547).

**Spec:** `docs/superpowers/specs/2026-10-01-m1-core-simulation-design.md` §7 ("**Stryker** mutation testing over `encounters`, `words`, `memory`, `production`, `sail`, `journeys`, `upgrades`, `grammar` and `automation`, run in CI with `break` at 90%") and story #36's five acceptance criteria.

## Global Constraints

- The nine modules, exactly: `encounters`, `words`, `memory`, `production`, `sail`, `journeys`, `upgrades`, `grammar`, `automation` in `packages/core/src` (AC1).
- `thresholds.break` = 90; a score under 90 fails the job (AC2).
- Every surviving mutant at merge time is killed by a new test or listed in the pull request with the reason it is equivalent (AC3).
- The job is in `develop`'s `required_status_checks.contexts` after its first merge, read back (AC4). The agent App gets 403 on that endpoint: Shyden runs the add.
- The HTML report is a CI artifact (AC5).
- The score may not drop (AC6, Shyden 2026-10-16: "fail on any drop", scoped to this repo's mutation run): every undetected mutant is on `stryker.equivalents.json` with its reason, and every entry there is still undetected.
- Mutation runs are CI's. The laptop runs unit tests, formatters, linters and type checks only (global rule, 2026-10-09).
- A non-unit suite keeps one measured limit, at its CI step, and none inside (#476). Its minutes are the smallest whole number at least 3 times its slowest measured run. Every job stops within 30 minutes (#44, `MAX_TIMEOUT_MINUTES`); no limit is raised.
- Warnings fail the build (`scripts/fail-on-warnings.sh`).
- Floors are recorded in CI only; the pull request is squashed into one commit before it is labelled `record-floors`, and the fetched floors are folded into that commit (#547, #544).
- Third-party actions pinned to 40-hex SHAs with `# vX.Y.Z`, the same as `ci.yml`.
- `Refs #36` in commits and the PR body; never a closing keyword.

## Decisions (researched, not asked: they are technical)

- **Unit tests only, no properties.** The properties suite draws fresh cases on every run (Shyden, 2026-10-12), so a mutant could be killed on one run and survive the next; the score would move with no code change. A survivor that only a property kills gets a named unit stand-in (AC3).
- **No unit setup in the Stryker Vitest config.** `tests/unit/setup.ts` fails a test over 0.1 s of its own CPU; Stryker's instrumented code is slower by design, so it would fail passing tests. The same tests run under that setup in the unit step. Stryker's own per-mutant timeout classifies a hanging mutant; it is a verdict on the mutant, not a limit on a test.
- **The TypeScript checker.** Vitest strips types, so a mutant that cannot compile would run and could survive, padding AC3's list of mutants to justify. The checker classes it `CompileError`, outside the score.
- **Static mutants kept** (no `ignoreStatic`): module-level tables are numbers this story protects. Their cost is measured in Task 4.
- **`coverageAnalysis: "all"`, not `"perTest"` (amendment 1, from run 1).** `@stryker-mutator/vitest-runner` 10.0.0 selects each mutant's tests with a `testNamePattern` of names joined by spaces; Vitest 5 matches `fullTestName`, joined by `>`, so no test in a `describe` ran and run 1 killed 6 of 1,291 (stryker-js#6210, fix unreleased). With `"all"`, core's planner gives every covered mutant the global filter (none here), so no name pattern is set, and uncovered mutants are still `NoCoverage`. Back to `"perTest"`: #603.
- **The drop rule is a list, not a recorded percentage (amendment 1).** A recorded score would also fail on every rise. The list is exact both ways, so the score can only fall by gaining an unlisted survivor. Dependabot's pull requests update it themselves: #604 (Shyden, 2026-10-16), blocked by this story.
- **The verdict lives in `ci-scope.ts`** beside the docs-only scope, one home for the doubt rules, rather than a sibling script or a `paths:` filter (a required check with a `paths:` filter never reports on other pull requests and blocks them).
- **Steps run on `mutation != 'skip'`**, so an empty or missing output runs Stryker (fail closed), as `ci.yml` uses `scope != 'docs-only'`.
- **Inputs beyond `packages/core/`**: `stryker.config.json`, `vitest.stryker.config.ts`, the root `package.json` and `package-lock.json`, `.nvmrc`, the workflow, `scripts/ci-scope.ts` and `scripts/fail-on-warnings.sh`. So Dependabot's npm pull requests run it too: a Vitest or Stryker bump can move the score.

## Review Focus

1. **(Answered by run 1: the initial run passed, 3,243 tests in 7 s.) The dry run under Stryker's sandbox.** Stryker copies the repository into `.stryker-tmp/` and runs the tests there; a core test that reads a fixture by a path outside that copy, or that relied on the unit setup, would fail the initial run. Pinned by Task 4's first CI run: the initial test run must pass.
2. **Duration against the 25-minute step and 30-minute job.** About 2,400 lines of mutated code, static mutants, and a type check per mutant. Pinned by Task 4's measured duration and Task 6's limit; over budget, the run is split across jobs by module, never given a higher cap.
3. **A warning in Stryker's own output** (a static-mutant notice, a checker notice) fails `fail-on-warnings.sh`. Pinned by Task 4: the step's log is read whole for `warn|deprecat|(!)`, and a warning's cause is fixed in config, never filtered out.
4. **A timed-out Stryker step writes no report**, so the upload then fails on `if-no-files-found: error`. Accepted: the Stryker step is the first red step and names the cause; Task 4 reads which step failed first.
5. **Dependabot's pull requests.** They run the job (the lock file is an input) with no secrets, which it needs none of. Pinned by the unit test that takes `package-lock.json` as an input.
